    #审批的是 exact action，不是一句模糊意图

    Reviewer 把自然语言建议转成 canonical action 后，才会创建审批。任何描述、目标或版本变化都会产生不同 digest，需要新的决定。

    #从 proposal 到 result

    Control intent
  -> ProposedAction + digest
  -> ApprovalRequest
  -> principal decisions
  -> target revalidation
  -> admission
  -> per target claim
  -> one use attempt permit
  -> gateway outcome
  -> host owned verification proof

    关键边界有三个：

    1. Approval 只授权与 digest 相同的 action。
    2. DispatchAttemptPermit 只能在持久事务消费 exact claim 后按值产生一次。
    3. Verification 只接受 host owned read source，不能接受 IM、cognition 或 actor hint 给出的结论。

    #多人策略与拒绝

    ApprovalPolicy 指定需要多少个不同 principal approval。重复决定被拒绝，任何一个有效 reject 都会结束 pending request。高风险策略可以要求两个不同 principal，而不是同一 principal 拥有的两个 channel。

    #CLI 操作

    cargo run -p agentic-reviewer-cli -- approval list
cargo run -p agentic-reviewer-cli -- approval read AR-7F30AB19
cargo run -p agentic-reviewer-cli -- approval decide \
  AR-7F30AB19 \
  --principal principal:... \
  approve

    拒绝时将最后一个参数改为 reject。

    #stale 与 expired

    Approval 有显式过期时间。即使 principal 已批准，只要重新验证发现 runtime revision、Git head 或 worktree digest 不再等于原 target version，动作会变为 stale。

    系统不会把旧决定迁移到新版本，也不会让 cognition 自动解释“用户大概仍然同意”。

    #no retry after ambiguity

    外部写调用存在经典不确定性：请求可能已经到达目标，但 response 在返回途中丢失。此时 Reviewer 记录精确 ambiguity stage，并进入 unknown，不自动重试。

    自动重试只适用于能够证明 not attempted 的结果。这个区分防止一个 interrupt、response 或未来 mutation 被执行两次。

    #route bound 生命周期通知

    来自 verified IM 的 approve 决定会绑定原 sender 与 conversation route。后续 Verifying、Succeeded、Failed、Stale、Expired 或 Unknown 通知只回到这个 exact route，不会广播给后来订阅的人。

    中间事件若已经落后于 canonical aggregate，会被 projector 抑制。通知系统不能审批、dispatch、retry 或 verify。

    #Codex 自身审批请求

    Reviewer 把实际观察到的 Codex pending request 投影为 metadata only CR-* prompt。Owner 或 Operator 可以发送精确选择：

    允许 CR-12345678
拒绝 CR-12345678

    提交 response 后状态仍可能只是 submitted，因为另一个订阅客户端可能先回答。Reviewer 不会把一次 wire submission 伪装成最终成功。
